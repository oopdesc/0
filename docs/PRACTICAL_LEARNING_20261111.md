# 実務学習の使い方と検証範囲

## 入口

- `/learn?section=workflow`：要件定義からリリース・運用まで8工程。各工程だけでも開始できる。テンプレートへ記入し、回答例・自己レビューと比較。8工程の成果物をZIP保存できる。
- `/learn?section=practice-lab`：自分で作るAPIテスト。正しいモデルでの期待値が一致した後に、6種類の不具合を検出できるか確認する。
- `/learn?section=practice-lab&lab=concurrency`：A・Bの更新順序を操作し、更新消失とversion照合を比較する。20操作まで。1操作戻す・再取得・再保存もできる。
- `/learn?section=practice-lab&lab=incidents`：4つの架空の障害事例。ログ・トレースから原因と再発防止を考える。
- `/learn?section=topics`：Java・Rustの16分野から、関係する問題だけを選んで復習する。Hibernate/JPAは通常問題と別の実装演習として検索できる。
- `/learn?section=practice-lab&lab=jpa`：Hibernate ORM・H2で4つの不具合を直す。楽観ロック、N+1、JPQLパラメータ化、rollback。開始コード・8件のJUnitテスト・回答例をZIP保存できる。

## おすすめの1セット

1. 要件定義で、利用者が何をしたいのか・対象外・受入条件を書く。
2. 基本設計でAPIの入出力と異常系を決める。詳細設計で層の責務と処理順序を決める。
3. 実務演習室で先にテスト項目・期待値を作り、基準モデルと照合する。不具合を見逃す項目を追加・改善する。
4. 「次はJava・Rustの実コードで確かめる」から開始ZIPを取得。片方の言語を選び、TODOを埋め、ローカルの実コンパイラでテストする。
5. HTTP・実DBは既存の小プロジェクトで確認する。実際の結果・証跡・未解決事項を各工程の成果物に追記する。
6. 障害事例の仮説・根拠・修正・回帰テストをメモへ残す。8工程ZIPと演習レポートを保存し、翌日また説明できるか確かめる。

一度に全工程を進める必要はない。単体テスト、実装、障害調査など、今必要な工程だけでも使える。回答例をコピーしただけの成果物は、自分で設計・実行した証拠とは分けて扱う。

## 実際に何が動くか

ブラウザのAPI・同時更新はTypeScriptで実装した練習モデル。HTTPサーバーや実DBへ通信しない。公開版では任意のJava/Rustコードをサーバーでコンパイルしない。有料API・有料DBは使わない。

開始ZIPのコードはJavaのjavac/java、Rustのrustcで実際に検証した。開始状態はコンパイル可能で、TODOのためテストが失敗。回答例を適用した状態ではJava 8/8、Rust 7/7が通過。開始状態の不合格を教材の故障と混同しない。

JavaのRepositoryはsynchronized、Rustは&mutでメモリ内状態を扱う。実DBの原子的な更新や分散システムの排他は別途実装・検証する必要がある。HTTP・SQLiteは既存の小プロジェクトへつなげる。

## 記録と誤認防止

- 試験項目・操作列・メモは既存の学習記録のdraft領域に保存し、バックアップの対象に含む。上限と形式を検査し、読み取れない既存記録を上書きしない。
- 試験項目を変えたら画面の実行結果を無効化する。基準モデルの期待値が一致しなければ、不具合の検出件数を確定しない。
- 6種類すべてを検出しても、すべてのバグがない証明にはならない。認証・実DB・通信等は別途試験する。
- 成果物を編集すると自己レビューを解除する。ZIPには未編集テンプレートの有無と自己レビュー件数を明記する。
- 8工程の記入・自己レビュー状況を表示し、前回の工程から再開できる。空欄・未編集テンプレートを記入済みに数えない。複数タブで同じ工程の下書きが変わった場合は上書きを止め、編集中のMarkdownを保存できる。
- 実務演習は就業経験・資格・リリース承認を与えるものではない。自分で書き、検証した成果物を残すための教材。
- 会社のコード・接続先・個人情報等は入力しない。記録は端末のブラウザにあり、別のURLや端末へ自動で引き継がれない。

## 今回の配信最適化

補充問題集の元JSONを、実行可能なJavaScriptに埋め込む方式から、ハッシュ付きJSONを必要時に取得する方式へ変更。教材の元データは変更せず、1130件の補充問題とリンク整合の検査を継続する。取得に失敗したら再読込を案内する。ビルド時とブラウザ時で同じ教材データを使う。

本番で発生した1MiB gzipの内部検査超過は、上限を引き上げることなく、この分離で解消する。これはVercelの無料利用量上限とは別の、リポジトリ内部のレビュー用予算。

## 自分のテストを実HTTPへ持ち出す

実務演習室のテスト設計から、自分の項目・期待値をJSONとPythonスクリプトのZIPで保存できる。学習専用loopback APIを自分で起動し、READMEの手順で実行する。別ホスト・資格情報付きURL・自動リダイレクト・システムプロキシを使わない。保存先停止の試験は別モードとして明示的に選び、未実行の項目はスキップと表示する。

モデルとの一致を実APIの合格に読み替えない。教材間のID・JSON・versionの契約差を比較し、変更要求として要件・設計・コード・テストを一緒に直す。

## Hibernate/JPAの実装課題

Java 17以上とMavenを使用。Hibernate ORM 7.4.15.Final、H2 2.3.232、JUnit 5.11.4を固定した。初回の依存取得以外は外部サービスへ接続しない。実運用DB・HTTP・Springの代わりになる教材ではない。

実際のMaven実行では、開始状態8件中4件が意図どおり失敗、回答例の4修正後は8件すべて成功、エラー・スキップ0件。テストごとに隔離したH2メモリDBを使い、管理対象とdetached・同一EntityManagerの同一性も制御テストで確認した。検証時刻・ソースハッシュ・結果は `JPA_WORKSHOP_VERIFICATION_20261111.json` に記録。

このJPA課題のversion初期値は0。手書きのAPIモデルの初期値1と同一とみなさない。SQLの回数は関連に実際に触れた後まで含めて確認し、LAZY指定だけをN+1解消の根拠にしない。
